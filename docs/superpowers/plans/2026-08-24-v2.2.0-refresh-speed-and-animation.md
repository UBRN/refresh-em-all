# Refresh Em All v2.2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the refresh operation measurably faster and the popup animations smooth, without adding a permission, collecting new data, or changing the install warning.

**Architecture:** Three independent edits to an existing MV3 Chrome extension. Part A (just-in-time media restoration) is already implemented on this branch and is only re-verified here. Part B removes a provably-dead 100 ms delay and halves two pacing constants in the background service worker. Part C moves the confetti animation off layout-triggering `top` onto compositor-friendly `transform`, and retimes the progress-bar transition to match the new, faster progress cadence.

**Tech Stack:** Manifest V3 Chrome extension, vanilla JS (no build step, no bundler, no framework), Jest + jsdom + jest-chrome for unit tests, Puppeteer for e2e.

## Global Constraints

- Spec: `docs/superpowers/specs/2026-08-24-v2.2.0-refresh-speed-and-animation-design.md`. It wins on any disagreement with this plan.
- No new manifest permission, no new `host_permissions`, no new dependency. `package.json` `devDependencies` must not change.
- No new data collection. Analytics is 2.3.0, permissions work is 2.4.0 — out of scope here.
- `content-script.js` must stay byte-identical. Verify with `git diff -- content-script.js` returning empty.
- The `@media (prefers-reduced-motion: reduce)` block in `popup.html` must not be modified.
- `#progressFill` must keep being driven by `style.width` as a percentage string. Six call sites read it; see Task 4.
- All existing tests must keep passing unmodified. Baseline before starting: `npx jest` reports 46 passing.
- Commit after each task. Do not bump the version until Task 5.

### Task 3: Move confetti off layout onto the compositor

`@keyframes fall` animates `top`, which triggers layout and paint on every frame. `showConfetti` creates 60 pieces, so this is 60 elements forcing layout for three seconds on the popup's main thread. Animating `transform` instead keeps the whole thing on the compositor.

A second, separate bug: piece durations are randomised over 2–4 s but cleanup is a fixed 3000 ms timeout, so the slowest pieces are deleted mid-fall.

**Files:**
- Modify: `popup.html:286-291` (`@keyframes fall`)
- Modify: `popup.js:351` (the random duration)

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces: nothing consumed by later tasks. `showConfetti()` keeps its signature and its early return on `prefers-reduced-motion`.

- [ ] **Step 1: Replace the keyframes**

In `popup.html`, replace:

```css
        @keyframes fall {
            to {
                top: 100%;
                transform: rotate(720deg);
            }
        }
```

with:

```css
        @keyframes fall {
            to {
                transform: translateY(calc(100vh + 20px)) rotate(720deg);
            }
        }
```

The `.confetti-piece` rule already sets `top: -20px` as the starting position; leave it alone. Translating by `100vh + 20px` carries the piece from 20 px above the viewport to fully past its bottom edge. Do **not** add `will-change: transform` — 60 promoted layers costs more than it saves, and a running `transform` animation is promoted automatically.

- [ ] **Step 2: Fix the cut-off pieces**

In `popup.js`, replace:

```js
        confetti.style.animationDuration = `${Math.random() * 2 + 2}s`;
```

with:

```js
        confetti.style.animationDuration = `${Math.random() + 2}s`;
```

Durations are now 2–3 s, which fits inside the existing 3000 ms cleanup timeout, so no piece is deleted while still visible. Leave the `setTimeout(..., 3000)` cleanup as it is.

- [ ] **Step 3: Run unit tests**

Run: `npx jest`

Expected: PASS, 47 tests. `tests/popup.test.js` does not assert on confetti geometry, so nothing here should need changing.

### Task 4: Retime the progress bar and status icons

The replacement must be no longer than the update interval, or it reproduces the same defect; 75 ms linear matches the cadence exactly, so each segment completes as the next arrives.

## Part A — already implemented, verify only

Just-in-time media restoration is already committed to this branch's working tree before this plan starts. It is described in the spec under "Part A". Do not re-implement it. Its behaviour is covered by these existing tests in `tests/background.test.js`, all of which must keep passing through every task above:

- `injects media restoration after a refreshed tab finishes loading`
- `does not inject media restoration while a refreshed tab is loading`
- `does not inject media restoration for a tab that was never refreshed`
- `does not schedule media restoration when capture finds no media`
- `schedules media restoration when the capture result shape is absent`
- `cancels pending media restoration when the tab is removed`
- `injects media restoration exactly once per refreshed tab`
- `does not inject media restoration when the reload itself failed`

Two invariants in that code are load-bearing and must not be "simplified" while editing nearby lines in Task 1:

- A tab is marked pending **after** `chrome.tabs.reload` is dispatched, never before. Marking earlier lets an already-loading tab reach `complete` for its *previous* navigation and consume the `sessionStorage` key in a document that is about to be discarded.
- The guard is `capturedCount !== 0`, not `> 0`, so an unexpected result shape still schedules a restore instead of silently dropping state.
