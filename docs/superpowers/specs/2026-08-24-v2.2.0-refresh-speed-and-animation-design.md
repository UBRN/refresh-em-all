# v2.2.0 — Just-in-time media restoration, refresh pacing, animation smoothness

Date: 2026-08-24
Status: approved, ready for implementation planning
Branch: `experiment/jit-media-restore`

## Why

Three separate complaints, one release:

1. The refresh operation feels slow.
2. Popup animations stutter.
3. `content-script.js` runs on every page load of every site for the life of the
   install, even though it does nothing unless this extension just refreshed
   that tab.

Item 3 was already implemented and verified on the branch before this spec was
written. Items 1 and 2 were investigated by measurement, not inspection, and the
findings changed the design twice. Both revisions are recorded below.

## Scope

In scope for 2.2.0:

- **Part A** — just-in-time media restoration (already implemented; documented
  here so the release has one coherent record).
- **Part B** — refresh pacing constants.
- **Part C** — popup animation smoothness.

Explicitly out of scope, each getting its own spec:

- **2.3.0** — local-first cache analytics ("tazelenen bayat önbellek"). Requires
  new in-page measurement, new storage rollups, new popup surface, and a
  `PRIVACY.md` update.
- **2.4.0** — moving `<all_urls>` to `optional_host_permissions` to downgrade the
  install warning. Affects existing users and store review; must ship alone.

Nothing in 2.2.0 collects new data, adds a permission, or changes the install
warning.

## Evidence

All numbers are `phasesMs.extensionOperation` from the existing e2e reliability
harness on this machine. Media restoration assertions passed in every run listed.

### Cost of Part A

20-tab profile, three runs each:

| build | runs | mean |
|---|---|---|
| `main` (2.1.0, declared content script) | 8368.7 / 8377.3 / 8362.2 | 8369.4 ms |
| branch (just-in-time injection) | 8453.9 / 8481.7 / 8468.3 | 8468.0 ms |

Part A costs **+98.6 ms across 20 tabs (~+4.9 ms per tab)**, from one extra
`executeScript` IPC per refreshed tab. In exchange, `content-script.js` stops
executing on every navigation on every site. Accepted.

### Pacing (Part B)

20-tab profile:

| `TAB_PROCESSING_INTERVAL` / `BATCH_INTERVAL` / pre-reload wait / batch size | operation |
|---|---|
| 150 / 500 / 100 / 5 — current | 8445 ms |
| 150 / 500 / **0** / 5 | 6297.2 ms |
| 75 / 250 / 0 / 5 | 3304.3 ms |
| 50 / 150 / 0 / 8 | 2218 ms |

50-tab profile, two runs each:

| config | runs |
|---|---|
| current | 31504.3 / 31567.7 ms |
| 75 / 250 / 0 / 5 | 21996.8 / 21958.5 ms |
| 50 / 150 / 0 / 8 | 20550.8 / 20594.2 ms |

Two conclusions:

- The 100 ms wait before each `chrome.tabs.reload` is dead weight. The
  `chrome.scripting.executeScript` callback already fires after the injected
  function has returned, so `sessionStorage.setItem` has landed by then. Removing
  it alone is a 25% win on 20 tabs with media restoration still passing.
- Past 75/250, returns collapse. At 50 tabs the aggressive config buys only 6%
  more while raising in-flight reloads from 5 to 8. The e2e fixture serves local
  pages that load instantly; real sites are heavier. Not worth it.

### Analytics metric probe (informs 2.3.0, recorded here so it is not re-litigated)

A local server with an ETag'd 50 KB asset, reloaded through CDP
`Page.reload({ignoreCache: true})` (what `bypassCache: true` maps to):

- Normal reload: only the document is requested; the asset is served from cache.
- Cache-bypassing reload: Chrome sends `Cache-Control: no-cache` and
  `Pragma: no-cache` and **no conditional headers at all** (`If-None-Match` absent).
  The server cannot answer 304. Resource Timing reports `transferSize: 51500` for
  the 50 KB asset — a full re-download.

A "bytes saved via 304" metric would therefore always read zero for this
extension. 2.3.0 will instead measure bytes that *were* being served from cache
immediately before the reload.

## Design

### Part A — just-in-time media restoration (implemented)

`manifest.json` no longer declares `content_scripts`. `host_permissions` and
`permissions` are unchanged.

`background.js` keeps a `pendingMediaRestores` map of tab id to expiry timeout.
`preserveStateAndRefreshTab` reads the capture result and marks a tab pending
**only after `chrome.tabs.reload` has been dispatched without error**, and only
when the capture did not report `count === 0`. A top-level
`chrome.tabs.onUpdated` listener injects `content-script.js` once when a pending
tab reports `status === 'complete'`; `chrome.tabs.onRemoved` cancels a pending
tab; entries expire after 30 s.

Two ordering decisions matter and must not be "simplified" later:

- **Marking happens after reload dispatch, not before.** A tab that was still
  loading when the refresh started can otherwise reach `complete` for its
  *previous* navigation, and the injection would consume the `sessionStorage` key
  in a document that is about to be discarded, silently losing the state.
- **The guard is `count !== 0`, not `count > 0`.** An unexpected or absent result
  shape must still schedule a restore, so the failure mode is a redundant
  injection rather than dropped state.

`content-script.js` itself is unchanged.

Known limitation, deliberate: the pending map lives in service-worker memory. If
Chrome evicts the worker between the reload and the tab reaching `complete`, that
tab's restoration is skipped and its media reloads from the start. Marked with a
`ponytail:` comment; upgrade path is `chrome.storage.session`.

### Part B — pacing

In `background.js`:

| constant | from | to |
|---|---|---|
| `TAB_PROCESSING_INTERVAL` | 150 | 75 |
| `BATCH_INTERVAL` | 500 | 250 |
| `MAX_TABS_PER_BATCH` | 5 | 5 (unchanged) |
| pre-reload `setTimeout` in `preserveStateAndRefreshTab` | 100 ms | removed |

`MAX_RETRIES`, `MAX_LOADING_WAIT_MS` and `MAX_TAB_REFRESH_MS` are unchanged.

**These two constants are not the whole pacing model.**
`refreshTabsInBatches` overrides both by tab count
([background.js:410](../../../background.js)):

| tab count | batch size | batch interval |
|---|---|---|
| ≤ 20 | `MAX_TABS_PER_BATCH` (5) | `BATCH_INTERVAL` |
| 21–50 | 4 (hardcoded) | `BATCH_INTERVAL` |
| > 50 | 3 (hardcoded) | 1000 ms (hardcoded) |

Consequences that the implementation must not misread:

- Raising `MAX_TABS_PER_BATCH` would only affect sessions of 20 tabs or fewer,
  which is why it is left alone rather than "kept at 5 for safety".
- Above 50 tabs, `BATCH_INTERVAL` is not consulted at all. The measured 50-tab
  improvement below therefore comes entirely from `TAB_PROCESSING_INTERVAL` and
  the removed pre-reload wait.
- The hardcoded `3` / `1000` path for >50 tabs is deliberately **not** touched in
  2.2.0. It is the highest-contention path, it already yields a 30% improvement
  without modification, and changing it would mean re-validating the profile
  where failure is most likely. Left as a candidate for a later release.

Expected: 20 tabs 8.4 s → ~3.3 s, 50 tabs 31.5 s → ~22.0 s.

### Part C — animations

**Confetti** ([popup.html](../../../popup.html), `@keyframes fall`; [popup.js](../../../popup.js) `showConfetti`).
The keyframe animates `top`, which triggers layout. With 60 pieces that is a
layout and paint on the main thread every frame for three seconds — the dominant
source of the stutter. Replace with `transform: translateY()` so the animation
stays on the compositor. The pieces already animate `rotate` in the same
`transform`, so both compose into one property.

Do **not** add `will-change` — 60 promoted layers costs more than it saves, and a
running `transform` animation is promoted automatically.

Separately, piece durations are randomised over 2–4 s but cleanup is a fixed
3000 ms timeout, so the longest pieces are cut off mid-fall. Narrow the random
range to 2–3 s so the existing timeout is correct.

**Progress bar** ([popup.html](../../../popup.html) `#progressFill`).
Keep `width`. The original design called for `transform: scaleX()`; that was
revised after finding that `style.width` is read in seven places
([tests/popup.test.js](../../../tests/popup.test.js) ×2,
[tests/e2e/reliability-scenario.js](../../../tests/e2e/reliability-scenario.js) ×2,
[tests/e2e/harness.js](../../../tests/e2e/harness.js),
[tests/e2e/run.js](../../../tests/e2e/run.js),
[tests/e2e/package-smoke.js](../../../tests/e2e/package-smoke.js)). Switching
would break all of them to fix a layout cost that does not exist for a single
element.

The real defect is timing: `transition: width 0.3s ease` restarts from a
partially-completed state every time progress arrives, and Part B shortens that
interval from 150 ms to 75 ms, which would make it visibly worse. Change to
`transition: width 75ms linear`.

The duration must be **no longer than** the update interval, otherwise every new
value still interrupts an unfinished transition — the exact defect being fixed.
Matching `TAB_PROCESSING_INTERVAL` at 75 ms means each segment completes just as
the next arrives. Real gaps are slightly longer and variable (75 ms plus reload
dispatch), so in practice a segment finishes and rests briefly rather than
jumping; with `linear` there is no re-acceleration, so that reads as steady
motion rather than stepping.

**Status icons.** `fadeIn` drops from `0.5s` to `0.15s` on `.tab-success`,
`.tab-error`, `.tab-skipped`. Half a second is too slow for a status flip that
now happens every 75 ms.

**Reduced motion.** The existing `@media (prefers-reduced-motion: reduce)` block
already neutralises durations and hides confetti. Unchanged.

## Testing

Unit (`npx jest`):

- Existing 46 tests must pass unmodified, including the `style.width` assertions
  in `tests/popup.test.js` — Part C is designed to keep them valid.
- Add a check that pins the removed 100 ms: with fake timers, after the
  `chrome.scripting.executeScript` capture callback has fired, `chrome.tabs.reload`
  must already have been called **without any `advanceTimersByTime` in between**.
  This fails if anyone reintroduces a delay on that path.

End-to-end, all must pass with media restoration:

- `npm run e2e`
- `npm run e2e:reliability:smoke`
- `npm run e2e:reliability:medium`
- `npm run e2e:reliability` (50 tabs) — the pacing change must be validated at
  the profile where contention is real, not only at 20 tabs.
- `npm run e2e:package`
- `npm run verify`
- `npm run package:verify`

Animation verification is visual and cannot be asserted by the existing harness.
Confirm by hand that confetti falls smoothly and that the progress bar advances
without stutter at the new 75 ms cadence.

## Risks

| risk | mitigation |
|---|---|
| Faster pacing overloads slow machines or heavy sites in ways the local-fixture e2e cannot show | Batch size held at 5; `MAX_LOADING_WAIT_MS`, `MAX_TAB_REFRESH_MS` and retries unchanged. Ship and watch reviews. |
| MV3 worker eviction skips a restore (Part A) | Disclosed in the store listing; `ponytail:` comment names `chrome.storage.session` as the upgrade. |
| Removing the 100 ms wait breaks capture on a machine slower than this one | The wait is provably after-the-fact — the callback already guarantees the write landed. Covered by a unit test. |
| Confetti `transform` change regresses reduced-motion behaviour | Reduced-motion block is untouched and already zeroes durations and hides the overlay. |

## Version and release

Version becomes `2.2.0` in `manifest.json` and `package.json`. Minor, not patch:
the content-script declaration is removed and refresh timing changes observably.
The store listing under `docs/chrome-web-store/` has already been updated for
Part A and needs no further change for Parts B and C.
